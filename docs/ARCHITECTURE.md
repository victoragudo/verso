# Verso Architecture

Verso is a free, open source (MIT) content management system built on Laravel 13. It aims to be a fast, modern and safe alternative to WordPress.

## Principles

1. 100% MIT. No paid edition, no locked features.
2. Fast by default: under 50 ms TTFB with page cache, Lighthouse 100 on the default theme.
3. Runs on cheap hosting: PHP-FPM with SQLite or MySQL. Octane is optional.
4. Typed and safe plugins: contracts, events and declared permissions. No string-based hooks.
5. One-click migration from WordPress.

## Stack

- Laravel 13, PHP 8.4+, Pest 5, PHPStan (Larastan), Pint.
- Admin: Inertia 3 + React 19 + Tailwind 4 + shadcn/ui components already in `resources/js/components/ui`.
- Editor: Tiptap (`@tiptap/react`, starter kit, image, link, placeholder).
- Images: `league/glide`.
- Default database: SQLite. MySQL and Postgres must also work (use portable schema and queries only).

## Code layout

Every feature lives in a module under `app/Verso/<Module>`.

```
app/Verso/<Module>/
  <Module>ServiceProvider.php   registers routes, nav items, bindings, events
  Models/                       Eloquent models
  Enums/
  Actions/                      single-purpose classes with a handle() method
  Http/Controllers/Admin/       admin controllers (Inertia)
  Http/Controllers/             public controllers
  Http/Requests/                form requests
  Policies/
  Console/                      artisan commands
routes/verso/<module>.php       loaded by the module provider
database/migrations/            see migration prefix table below
resources/js/pages/admin/<module>/*.tsx
resources/js/components/verso/<module>/*.tsx
tests/Feature/<Module>/  tests/Unit/<Module>/
```

Module providers are registered in `bootstrap/providers.php`. This file is the only shared file a module may touch, and only to add one line.

## Core contracts (built in the Foundation phase)

### Admin

- All admin routes live under `/admin`, use the `auth` and `verified` middleware and the route name prefix `admin.`.
- `App\Verso\Core\Admin\AdminNav` is a singleton. Modules add items in their provider `boot()`:
  `AdminNav::add(new NavItem(key: 'media', label: 'Media', route: 'admin.media.index', icon: 'media', order: 30, capability: Capability::UploadFiles))`.
  `icon` is a key from the Verso icon set (`resources/js/components/verso/icons`), like `media` or `settings`. Unknown keys show a small ring. `group` is a `NavGroup` and picks the sidebar section: `Dashboard`, `Content`, `Design`, `Tools`, `Administration`, `Settings` (in that order, default `Content`). `parent` puts the item inside another item (Categories inside Posts, Invitations inside Users). `keywords` are extra search words for Cmd+K (synonyms, other languages: "sales", "pedidos"). An item with `route: ''` only groups its children and links to its first visible child (System). `fragment` adds `#part` to the link.
- Items are shared to Inertia as the `versoNav` prop: a flat list in sidebar order (each child right after its parent) with `key`, `label`, `href`, `icon`, `group`, `parent`, `keywords`, `plugin` and `isNew`. Only items the user may open are sent: the item `capability` and every `can:` middleware of its route must pass, links to routes that do not exist are dropped, a child of a hidden parent moves to the top of its group, and a group item without visible children is dropped. So hidden items never reach the sidebar or Cmd+K. `AdminNav::path($key)` gives labels like `['Tools', 'Shop', 'Orders']`.
- The menu: Dashboard (plugin dashboard pages, like Analytics, are tabs on the dashboard) | Content: Posts (Categories, Tags), Pages, Media, Comments, then plugin content types (order `ContentAdminNav::PLUGIN_TYPE_ORDER` + menu order) | Design: Guided start, Make it yours, Site Editor, Theme builder, Library, Themes, Menus, Custom code | Tools: one item per plugin | Administration: Users (Invitations, Roles), Plugins and themes, Import, Updates, System (System settings, Server health) | Settings: Your site details, General, Permalinks and SEO (SEO overview, Redirects, 404 monitor), Editor, Custom fields, plugin settings like AI Assistant.
- Plugins place their pages with the `admin` part of `verso.json` (see EXTENDING.md). `Plugins\Admin\PluginNavPlacement` adds them: Tools plugins (and any plugin with several links) get one parent item `plugin.<slug>`, `dashboard` links become dashboard tabs, one link in another group is a plain item. Items a plugin adds in PHP with `addNavItem()` are moved to the declared place (Tools when the manifest has no `admin` part). `location($plugin)` gives "Tools > Shop" for the plugin card and the toast shown after enabling it.
- "New" badge: `NavNewBadges` marks items of plugins enabled in the last `verso.admin.nav.new_badge_days` days (`plugins.enabled_at` setting) until the user opens them; opened keys are kept per user in `users.admin_preferences` (`AdminPreferences`, last `verso.admin.nav.max_seen`). The page that matches the request counts as opened.
- Sidebar state: sections and parents open and close; the choice is kept per user in localStorage (`verso.nav.<userId>`, read and written in try/catch). The section and parents of the current page always open. After enabling a plugin the server flashes a toast with an Open button (`action.navKey`) and `navHighlight`, which highlights the item for a moment.
- The admin layout is `AppLayout`, which renders the Verso admin shell (`resources/js/components/verso/shell`). The sidebar reads `versoNav` and the `siteName` prop.
- Load a module's admin route file with `App\Verso\Core\Routing\AdminRoutes::load(base_path('routes/verso/<module>.php'))`. It adds the `/admin` prefix, the `admin.` name prefix and the `web`, `auth`, `verified` middleware.
- Admin lists (`DataTable`): columns can be `optional` with a `defaultFrom` width (`always`, `md` 48rem, `lg` 64rem, `xl` 80rem, `2xl` 100rem, `3xl` 125rem, `never`). The table is a `@container/table`; without a saved choice optional columns show from their width, so ultrawide screens show more columns, and the title column keeps a percentage width (45%, 32% from 80rem, 24% from 125rem). The View menu (`ColumnChooser`) picks columns and the density (comfortable or compact). `useListView()` saves the choice with `PUT admin/list-views/{list}` into `users.admin_preferences` (`AdminPreferences::listView()`, `listViewProps()`); pages get it as the `listView` prop. Lists with views: `entries.<type>`, `comments`, `users`, `forms.submissions`, `shop.products`.
- Entry list columns: `Content\Admin\EntryListColumns` gives the optional columns of a content type (featured image, one per taxonomy, word count, last modified, SEO status; Comments adds a comment count) and their values (`row.columns`). Terms and featured images load with one query each, counts are `withCount` in the main query, and the status counts (one grouped query, trash included) give the page total, so the list stays inside its query budget. Plugins add columns with `AdminEntryColumnsFilter` (`ListColumn` with `with` and `withCount` relations).
- Dashboard counts: `app(App\Verso\Core\Admin\Dashboard::class)->addStat(new DashboardStat(key:, label:, count: fn () => int, order:, capability:, route:, parameters:, icon:))`. `icon` is an optional key from the Verso icon set, shown in the stat card. Register nav items and stats that call `route()` inside `$this->app->booted(...)` or lazily, never during `register()`.
- Flash messages: `Inertia::flash('toast', ['type' => 'success', 'message' => '...'])`.

### Roles and capabilities

Module `App\Verso\Access` (provider `AccessServiceProvider`, routes `routes/verso/access.php`). How plugins declare capabilities and roles: EXTENDING.md, "Capabilities and roles".

- Capabilities: `Access\Capabilities\CapabilityRegistry` (singleton) holds every capability with label, description, group, section, risk (`Enums\RiskLevel`) and `implies`: core (`Core\Enums\Capability` + `CoreCapabilities`), seven per content type (`entries.<type>.<action>`, `Enums\EntryAction`), plugins (`capabilities` in `verso.json`, registered by `PluginManager::register()` through `ManifestAccess`) and the active theme (`theme.json`). Old names stay valid; umbrellas imply the new fine grained keys (`manage_users`, `manage_settings`, `manage_plugins`, `manage_themes`).
- Roles: `users.role` (enum `Core\Enums\Role`: `admin`, `editor`, `author`, `contributor`, `subscriber`, optional `shop_manager`) is the main role. Extra roles per user live in `role_user` (any role slug), single grants or denies in `user_capabilities`. `Access\Roles\RoleRegistry` has the roles from code (built-in defaults from `Role::capabilities()` plus plugin defaults; plugin roles from manifests), `Access\Roles\Roles` merges them with the `roles` table (custom roles; built-in roles store only added and removed capabilities). The administrator role is locked: always every capability.
- Checks: `User::hasCapability(Capability|string)` asks `Access\Permissions\UserPermissions` (roles, then grants, then denies with what they imply; cached per user object, `refreshAccess()` clears it). A `Gate::before` hook answers every registered capability, so `can:` middleware and `$user->can('forms.messages')` work. Entries: `EntryPolicy` with `Access\Permissions\EntryPermissions` (capability for every type or for one type; without `read_private` the list shows only own entries and published ones of others). Optional roles (`OptionalRoles::enable()`) are listed only when their plugin is on.
- Safety: `Access\Support\EscalationGuard` (nobody gives a capability or role they do not have; only people with at least the same access change someone else; changing your own access may only lower it) and `Users\Support\AdminGuard` (the last administrator, as main or extra role, stays). `UserPolicy` uses `list_users`, `create_users`, `edit_users`, `promote_users` and `delete_users`.
- Every admin route has a `can:` middleware (allow list: `admin.dashboard`, `admin.list-views.update`, `admin.view-as.stop`), checked by `tests/Feature/Access/AdminRouteCapabilitiesTest.php`. Composite abilities: `Access\Support\AccessAbilities` (`verso.custom-code`, `verso.install-extensions`).
- Admin: Administration > Users > Roles (`admin.roles.*`, capability `manage_roles`): the matrix of roles and capabilities (`PUT admin.roles.matrix`), one page per role (members, defaults, change log, clone, reset, delete, view as), compare (`?roles=editor,author`, up to `verso.access.compare_limit`). User access page `admin.users.access.edit` (`promote_users`): main role, extra roles, grants and denies.
- Inertia shares `can` (capability key => bool) and `viewAs`. Nav items, dashboard stats, panels, notices and slot items take a capability, a gate ability or a closure (`Access\Support\Ability`).
- "View as role": administrators preview the admin as another role (`POST admin.roles.view-as`, session key `verso.view_as_role`, middleware `verso.view-as` in `AdminRoutes::MIDDLEWARE`). Everything answers as that role, every non GET request except `admin.view-as.stop` is refused, and the shell shows a banner.
- Audit: role and access changes go to `system_config_changes` (actions in `AccessAudit::ACTIONS`); the System settings log hides them.
- `manage_system` (`Capability::ManageSystem`) opens System settings and Server health; only admins have it by default.

### Settings

- `settings` table (key, JSON value). `App\Verso\Core\Settings\Settings` service with `get(string $key, mixed $default = null)`, `set(string $key, mixed $value)`, cached in memory and in the cache store.
- Known keys: `site.name`, `site.tagline`, `site.url`, `site.locale`, `site.timezone`, `reading.posts_per_page`, `reading.front_page` (null or entry id), `theme.active`, `plugins.enabled`.
- Dates are stored in UTC. `App\Verso\Core\Support\SiteTime` shows them in the `site.timezone` zone (`local()`, `iso()` with offset, `format()`) and reads typed dates back to UTC (`toUtc()`). The admin gets the zone as the `siteTimezone` prop and formats dates with `useSiteDates()` or `<SiteDate>`. The publish date field sends the wall time in the site zone and the server converts it to UTC. The theme, comments, feed, sitemap and SEO tags print dates in the site zone.

### Redirects

- `redirects` table (`from_path` unique, `to_path`, `status_code` 301 or 302, `hits`). Model `App\Verso\Core\Models\Redirect`. Create them with `Redirect::point($from, $to, ?$status)` (it avoids chains and loops). The middleware alias `verso.redirects` applies them: the Theme module adds it to every public route. The importer and the slug change logic create them.

### Content

- `content_types` are defined in code through `App\Verso\Content\ContentTypeRegistry` (singleton). Built-in: `post` (hierarchical: false, has archive: true, route base `blog`) and `page` (hierarchical: true, no archive, route base ``). Plugins can register more.
- `entries` table: `id`, `type`, `title`, `slug`, `status`, `blocks` (JSON), `excerpt`, `author_id`, `parent_id`, `menu_order`, `published_at`, `meta` (JSON), `timestamps`, `soft deletes`. Unique index on `(type, slug, parent_id)`.
- Enum `EntryStatus`: `draft`, `scheduled`, `published`, `trash` (trash also uses soft delete).
- Domain methods on `Entry`: `publish()`, `schedule(CarbonInterface $at)`, `unpublish()`, `isPublished()`, `url()`, scope `published()`. A scheduled job publishes due entries every minute.
- `revisions` table: an entry snapshot (title, blocks, excerpt, meta) saved on each update. Keep the last N (setting `content.revisions_limit`, default 25).
- `taxonomies` are defined in code through `TaxonomyRegistry`. Built-in: `category` (hierarchical) and `tag`. `terms` table (`taxonomy`, `name`, `slug`, `parent_id`, `description`). `entry_term` pivot.
- Event classes: `EntrySaved`, `EntryPublished`, `EntryDeleted`. The cache and the sitemap listen to them.
- Actions in `App\Verso\Content\Actions`: `CreateEntry`, `UpdateEntry`, `PublishEntry`, `ScheduleEntry`, `TrashEntry`, `RestoreEntry`, `RestoreRevision`, `CreateTerm`, `UpdateTerm`, `DeleteTerm`. Always change entries through them so revisions, redirects and events stay correct.
- Admin routes use the parameters `{contentType}` and `{taxonomy}` (bound to `ContentType` and `Taxonomy` objects, 404 when unknown): `admin.entries.*` under `/admin/entries/{contentType}` and `admin.terms.*` under `/admin/terms/{taxonomy}`.
- Public URLs: `Entry::path()` / `url()` and `Term::path()` / `url()`. Use them, never build URLs by hand.

### Blocks (the content format)

`entries.blocks` stores a JSON array. Each block is:

```json
{ "id": "b_k2j3h4", "type": "paragraph", "attrs": { }, "content": "<p>Inline <strong>HTML</strong> limited to inline marks</p>", "children": [] }
```

- `type` is a registered block name. Core blocks: `paragraph`, `heading` (attrs.level 1 to 6), `list` (attrs.ordered), `quote`, `code` (attrs.language), `image` (attrs.mediaId, src, alt, caption, width, height), `gallery` (attrs.mediaIds), `embed` (attrs.url), `columns` (children are `column` blocks), `column`, `separator`, `button` (attrs.url, label, style), `html` (raw, admin only), `table`, `video`.
- PHP `App\Verso\Editor\BlockRegistry` maps types to `App\Verso\Editor\Contracts\Block` renderers. `App\Verso\Editor\BlockRenderer::render(array $blocks): string` returns safe HTML. Inline HTML is sanitized against an allow list. Unknown block types render nothing. A block whose renderer throws (core or plugin, through `BlockRenderer::safely()`) is reported with `report()` and left out, so one broken block never takes the page down; in edit mode (`showMarkers()`) it becomes a short note with the block markers that the visual editor can delete.
- `ValidBlocks($user, stored: $entry->blocks)` lets a user without a block's capability (like `html`) save an entry again when that block is kept unchanged from the stored blocks (same id, type, content and attrs). Any change still needs the capability.
- The JS editor component lives at `resources/js/components/verso/editor/block-editor.tsx` with props `{ value: Block[]; onChange: (blocks: Block[]) => void }`. Types live in `resources/js/types/verso.ts`.

### Media

- `media` table: `disk`, `path`, `filename`, `mime_type`, `size`, `width`, `height`, `alt`, `caption`, `uploaded_by`, `meta`.
- Media picker component: `resources/js/components/verso/media/media-picker.tsx` with props `{ open: boolean; onOpenChange: (open: boolean) => void; onSelect: (media: MediaItem) => void; accept?: 'image' | 'video' | 'any' }`.
- JSON endpoint for the picker: `GET /admin/media/library` (paginated, searchable).
- Image URLs: `/img/{path}?w=&h=&fm=webp|avif|jpg&q=` served by Glide with signed URLs and a disk cache.

### Themes

- Themes live in `themes/<slug>/` with `theme.json` (name, version, description, author, `parent`, `templates`, settings schema) and Blade views in `themes/<slug>/views`. The `theme` view namespace looks in the active theme, then its parents, then `themes/default`, then plugin view folders. Full guide: `docs/THEMES.md`.
- Required views: `layouts/app`, `home`, `entry`, `archive`, `taxonomy`, `search`, `404` (a child theme gets them from its parent or the default theme).
- Child themes: `"parent": "<slug>"`. Settings schema, page templates and block patterns are inherited (the child wins on the same key), parent CSS is printed before child CSS, `ThemeManager::lineage()` lists the chain and `missingParent()` blocks activation. The parent of the active theme cannot be removed. `php artisan verso:make-theme "Name" --parent=<slug>` makes one.
- Template hierarchy (`Theme\Templates\TemplateHierarchy`, typed by `TemplateContext`): entry `[page template view], [front-page], entry-{type}-{slug}, entry-{type}-{id}, entry-{type}, entry`; term `taxonomy-{taxonomy}-{slug}, taxonomy-{taxonomy}, taxonomy, archive`; archive `archive-{type}, archive`; author `author-{slug}, author, archive`; `home`, `search`, `404`. Plugins change a list with `TemplateCandidatesFilter` (`fn (array $candidates, TemplateContext $context, ?object $subject): array`). `ThemeResponse::render()` uses the first view that exists.
- Page templates: `theme.json` `templates` (`label`, `description`, `view` default `templates.<name>`, `types` default `["page"]`). The entry editor gets `pageTemplates` and saves the name in `entries.meta.template` (reserved meta key).
- Template parts: `views/parts/<name>.blade.php` and variants `<name>-<variant>`, included with `@templatePart('footer', 'minimal')`. The default theme header and footer are parts.
- Block patterns: `patterns/*.json` (`name`, `title`, `category`, `description`, `keywords`, `blocks`), max size `verso.themes.pattern_max_kb`. Shared with the entry editor as `blockPatterns` and inserted with the "Patterns" button.
- Template debug: users with `manage_themes` add `?verso-template-debug=1` (`verso.themes.template_debug.*`) to see the checked candidates in a panel; such pages are never cached.
- `<x-verso-featured-image :entry="$entry" />` prints the entry's featured image (`meta.featured_image.mediaId`) with a srcset, or nothing. The default theme shows it on entry cards and on the entry page. With `:skip-lead-image="true"` it prints nothing when the first block is an image block with the same `mediaId`, so the image never shows twice.

### Plugins

- Plugins live in `plugins/<slug>/` (or as Composer packages) with a `verso.json` manifest: `name`, `slug`, `version`, `description`, `provider` (FQCN), `requires` (verso version), `permissions` (list of capabilities it needs), `admin` (where its admin pages go in the sidebar, see EXTENDING.md).
- Plugins and themes (`admin.plugins.index`, tabs `plugins`, `themes`, `add`, `browse`) is the one page for installed plugins, installed themes, uploads and the registry. `/admin/extensions` redirects to the `add` or `browse` tab; upload, review, install and remove keep their `admin.extensions.*` routes.
- A plugin provider extends `App\Verso\Plugins\PluginServiceProvider`. It can register blocks, content types, taxonomies, nav items, routes and event listeners. Typed filters through `App\Verso\Plugins\Filters` (for example `Filters::add(EntryContentFilter::class, fn (string $html, Entry $entry) => $html)`).
- A plugin block implements `App\Verso\Plugins\Contracts\PluginBlock`. It can also implement `HasBlockFields` (`description()` and `fields()` returning `BlockField` objects: text, textarea, number, url, toggle or select). The fields give the attrs validation rules and are shared with the entry editor as the `pluginBlocks` prop, so the block shows in the slash menu and the "Add block" menu with a generated form.
- Composer packages are plugins when their `composer.json` has `extra.verso`: either the manifest object itself (`slug` defaults to the package name part, `version` to the package version) or `true` (or a file name) to read `verso.json` in the package folder. They are read from `vendor/composer/installed.json` (`verso.plugins.composer_installed`). A plugin folder wins over a package with the same slug.
- Enabled plugins are stored in the `plugins.enabled` setting.
- Plugin config: put files in `config/` (`verso.plugins.config_path`) and call `$this->mergeConfigFrom($this->path('config/<key>.php'), '<key>')`. `PluginServiceProvider` overrides it through `Support\PluginConfig`, so it works with `php artisan config:cache`: in the console every plugin's config files are loaded (enabled or not), so the cache stores them with their env values, and with a cached config a missing key (a plugin added after caching) is still filled from the file. Values already in the config win over the file.
- `ThemeFooterFilter` (`fn (string $html, Request $request): string`) adds HTML at the end of every public page. Themes print it with `<x-verso-footer />` before `</body>` (the default theme and the `verso:make-theme` stub do). For themes that do not, the `verso.footer` middleware (`InjectThemeFooter`, part of the public middleware, inside the page cache) adds it before the last `</body>` of HTML responses; the component marks the request, so the HTML is never printed twice. Plugin public routes that render theme pages add `verso.footer` too. The HTML is printed as it is, never compiled as Blade, and it is stored in the page cache, so it must not depend on the visitor.
- Every typed filter and admin slot is listed with examples in `docs/EXTENDING.md`. Filters live in `app/Verso/Plugins/Filters` and cover public lists (`EntryQueryFilter` with an `ArchiveContext`), search results, block HTML, head tags (`HeadTag` objects, printed by `<x-verso-head />`), body classes (the `$bodyClass` layout variable), SEO data (`SeoPage::with...()`), sitemap rows (`SitemapUrl`), feed items (`FeedItem`), outgoing mail (`OutgoingMail`, can be cancelled), admin nav items, entry table rows, entry permissions (`EntryAbility`), upload rules and public routes (`$this->addPublicRoutes()`). Themes print `<x-verso-head />` in `<head>` and `{{ $bodyClass }}` on `<body>` (single entries get `single type-{type} slug-{slug}`, never `entry`, so `.entry` stays free for the article).
- Admin slots: `$this->addAdminSlot(new SlotItem(slot: AdminSlot::..., key:, component:, label:, capability:, order:, props:))`. `props` is an array or a closure that gets the request (null hides the item). `AdminSlotRegistry` shares the items as the `versoSlots` prop (by slot name, like `entry-sidebar`), only on the screen of the slot and only for users with the capability. In React, plugins register components by key from `plugins/<slug>/resources/js/index.tsx` (default export `register(registry)`), loaded by a Vite glob in `app.tsx`; screens render them with `<Slot>` / `useSlotItems()` from `@/components/verso/slots`. The SEO card (`site.seo`), the comments switch (`comments.switch`) and the AI assistant (`ai-assistant.panel`) are slot components.

### Analytics plugin (`plugins/analytics`)

- Privacy first: no cookies, no personal data. The beacon (`Support\Beacon`, under 1 KB, printed through `ThemeFooterFilter`, so it is inside cached pages) stops on Do Not Track or Global Privacy Control and sends `p` (path), `r` (referrer host, empty for links inside the site) and `w` (`mobile`, `tablet` or `desktop`) with `navigator.sendBeacon` to `POST /_verso/collect` (`analytics.endpoint`). The route has no session or CSRF, only the `verso-analytics` rate limiter, and always answers 204.
- The server checks DNT and `Sec-GPC` again, drops bots (`analytics.bots` words, empty user agents), admin paths and bad data. Logged-in users whose role is in the `analytics.ignore_roles` setting get no beacon (default from `analytics.defaults.ignore_roles`, `ANALYTICS_IGNORE_ROLES`, `admin`; an old `analytics.ignore_admins` switch is still read until roles are saved). Pages for logged-in users are never cached.
- Tables: `analytics_events` (raw views: `day`, `path`, `referrer_host`, `device`, `visitor`), `analytics_daily` (`day`, `dimension` = total, page, referrer or device, `value`, `views`, `visitors`) and `analytics_salts`. `visitor` is `sha256(daily salt, IP, user agent, host)`; the salt of a day is deleted once the next day starts, so visitors cannot be linked across days. Days are in the site time zone. Visitors over a range are the sum of daily unique visitors.
- Private paths are never counted and get no beacon: `Support\PathExclusions` checks the `analytics.exclude_paths` patterns (`/admin` covers the path and everything under it, `*` is a wildcard; `ANALYTICS_EXCLUDE_PATHS` adds more), path parts that look like tokens (UUIDs, long runs of mixed letters and digits, `analytics.token_min_length`) and query keys in `analytics.sensitive_query_keys` (the beacon also checks them in the browser). Plugins add patterns with the core `PrivatePathsFilter` (`fn (array $patterns): array`): the shop adds cart, checkout and its webhook, the newsletter adds `/newsletter`.
- `RollupAnalytics` runs daily at `analytics.rollup_at`: it rolls up every past day without daily rows (`RollupDay` is idempotent), then deletes raw events older than the `analytics.retention_days` setting and old salts. `php artisan analytics:rollup [--day=Y-m-d] [--no-prune]` does the same by hand.
- `AnalyticsReport::build($days)` reads daily rows and counts days that are not rolled up yet (like today) live from raw events. Admin page `admin.analytics.index` (`?range=7|30|90`, capability `analytics.capability`, default `analytics.view`; settings also need `manage_settings`) renders `admin/plugins/analytics/index`; settings are saved with `admin.analytics.settings.update`. The dashboard gets a "Visitors today" stat.

### Install wizard

- Module `App\Verso\Install`. On first start `bootstrap/app.php` calls `Env\EnvironmentFile::ensure()`: a missing `.env` is copied from `.env.example` with a fresh `APP_KEY` (an empty `APP_KEY` is filled too). Skipped when `APP_ENV=testing` or `VERSO_INSTALL_CREATE_ENV=false`.
- Until the lock file (`verso.install.lock_file`) exists, the global `RedirectToInstaller` middleware sends every request (except `/install/*` and `/up`) to `/install` (JSON clients get 503) and `InstallerMode` forces file sessions (encrypted), file cache and the sync queue. Old installs with an admin and no lock file get the lock on their first request. `verso.install.redirect` (false in `phpunit.xml`) turns it off.
- The wizard routes use the `verso.installer` middleware group (the web group without anything that reads the database) plus `EnsureNotInstalled` (404 once installed). Steps (`Wizard\WizardStep`): welcome, requirements, database, site, services, content, review, install. Answers live in the session (`Wizard\WizardStore`); `Wizard\StepRules` validates each step for the web and the command. Secrets (`Wizard\SecretFields`) are never sent back to the browser; an empty field with `keep[]` keeps the saved value.
- `Database\DatabaseConnectionTester` (short PDO timeout, `PdoConnector` is replaceable in tests) maps errors to `ConnectionProblem` (host unreachable, auth failed, unknown database, version too old, ...), checks `min_versions`, existing Verso tables and the right to create a database. `Database\DatabaseCreator` creates the SQLite file or runs `create database`. Test endpoints (`/install/test/*`) use the `verso-install-tests` rate limiter.
- `Pipeline\InstallPipeline` runs `InstallStep` classes (write .env with `Env\EnvWriter`, prepare database, migrate, create admin, save settings, demo content (`DemoContentSeeder`), plugins, storage link, finish: `install.completed_at` setting plus lock file). Progress is kept in `verso.install.state_file`, so a failed step is retried without redoing done steps. The web page posts `/install/run` once per step; at the end it gets a one-time signed link (`verso.welcome`) that signs the admin in. `RuntimeConfig` points the running app at the chosen database before each step. Errors are redacted with `InstallPlan::redact()`.
- `php artisan verso:install` asks the same questions with Laravel Prompts or runs without questions (`--no-interaction` with `--db-*`, `--site-*`, `--admin-*`, `--mail*`, `--cache`, `--session`, `--queue`, `--demo`, `--theme`, `--plugins`, `--force`; missing values come from `DB_*` and `VERSO_INSTALL_*`). It refuses to run on an installed production site, even with `--force`.

### Extensions (install, update, remove)

- Module `App\Verso\Extensions`. Uploads and the registry live on the Plugins and themes page (`admin.plugins.index`, tabs "Add new" and "Browse"); the old `admin.extensions.index` URL redirects there. A consent screen `admin.extensions.review` (`/admin/extensions/review/{token}`) that lists the requested permissions. Nothing is installed before the admin accepts.
- `PackageInspector` checks every zip before it is unpacked: size (`verso.extensions.max_upload_kb`), unpacked size (`max_unpacked_kb`, also enforced while unpacking), file count, no absolute paths, no `..`, no backslashes or control characters, no symlinks or special files, no encrypted entries, no duplicates, no hidden files, only `allowed_extensions` (plus `allowed_plain_files` like LICENSE). Plugin PHP files must sit in `plugin_php_folders` or the manifest autoload folders. Theme PHP files must be Blade views inside `views/`. The manifest (`verso.json` or `theme.json`) must be at the top, or inside one top folder.
- `ExtensionInstaller`: `stage()` keeps the zip in `verso.extensions.storage_path/staging/<uuid>` (expires after `staging_ttl_minutes`), `install($token, $activate)` unpacks to a temp folder, moves the old version to `backups/<kind>/<slug>/` (keeps `backups_kept`), moves the new one in place, then enables the plugin (when asked or when it was enabled) or activates the theme. Any failure rolls back to the backup. Older versions are refused. `remove($kind, $slug, $deleteData)` disables a plugin, then deletes its folder. With `$deleteData` (`delete_data` on `DELETE admin.extensions.remove`), `Actions\DeleteExtensionData` first runs the plugin migrations down (`PluginMigrator::rollback()`) and deletes its settings (keys starting with `<slug>.`), or deletes a theme's settings (`theme.<slug>.`) with `Settings::forgetPrefix()`. Without it the data stays for a later install. The Plugins and Themes pages ask with `RemoveExtensionDialog` ("Remove, keep data" or "Remove and delete data"). The active and fallback themes cannot be removed. Only folders inside the install path (first `verso.plugins.paths` entry, or `verso.themes.path`) are touched.
- Plugin migrations: a plugin may ship `database/migrations` (`verso.plugins.migrations_path`). `EnablePlugin` runs them through `PluginMigrator` while `verso.plugins.migrate_on_enable` is on; a failure disables the plugin again. Enabled plugins add the folder to the migrator, so `php artisan migrate` runs them too. A provider can also call `$this->loadPluginMigrations()`.
- Registry: `verso.extensions.registry.url` (empty turns Browse off) returns JSON, a list or `{"extensions": [...]}`, with `type` (plugin or theme), `name`, `slug`, `version`, `description`, `download_url` (https only) and `sha256`. `StageRegistryPackage` downloads the zip, checks the sha256 sum and that slug and version match, then stages it like an upload.

### Plugin verification

- Every plugin is checked between upload (or registry download) and the consent screen. `VerifyStagedPackage` unpacks the staged zip into `verso.extensions.storage_path/verify/<uuid>`, runs `PluginVerifier::verify($path)` and stores the report in `plugin_verifications` (model `App\Verso\Extensions\Models\PluginVerification`) with the staging token and the zip sha256. The review screen reuses the report while the zip is unchanged. Theme zips are verified too (see "Theme verification" below).
- `PluginVerifier` runs, in order: `PhpScanner` (PHP tokenizer, `token_get_all`) on every `.php` file, `AssetScanner` on Blade views (raw output, inline scripts, data printed in scripts, external scripts, plus `@php` blocks as PHP) and on `verso.extensions.verification.script_extensions` files, `PermissionCheck`, the sandbox, then `CompatibilityCheck`. `node_modules` and `.git` are skipped; files over `max_file_kb` give `scan.file-too-large`.
- A `Finding` has a `rule` (like `php.eval`, `php.shell`, `php.obfuscated-code`, `php.dynamic-include`, `php.file-write`, `php.raw-sql`, `php.network`, `js.external-script`, `blade.script-injection`, `permission.undeclared`, `permission.undeclared-network`, `compat.table-clash`, `sandbox.migration-failed`), a `Severity` (`info`, `low`, `medium`, `high`), a message, a file inside the plugin and a line.
- Score: each severity has a weight (`verification.weights`). Code rules (`php.*`, `js.*`, `blade.*`) count once per rule and file; other rules once per distinct problem. `RiskLevel` is `high` when any finding is high or the score reaches `high_score`, `medium` from `medium_score`, else `low`.
- Permissions: `CapabilityMap` maps what the code uses to capabilities (Verso actions by class or namespace, static model writes like `User::create()`, `Settings::set()`, `Storage` writes). Used but not declared gives `permission.undeclared`; declared but unused gives `permission.unused` (info). The manifest may list `network` hosts (`"network": ["api.stripe.com", "*.example.org"]`); every host named in a file that makes network calls, in `config/` or in browser requests must be listed.
- Compatibility: `requires` against `verso.version`, a `php` constraint in verso.json or `require.php` in composer.json, Composer packages and `ext-*` from composer.json, and clashes with the site and other installed plugins: slug (Composer package plugin), tables (`Schema::create` in migrations), config keys (`config/*.php` and `mergeConfigFrom`), classes and PSR-4 namespaces, routes, content types and taxonomies (from the sandbox). The installed version of the same plugin never clashes with itself.
- Sandbox (`SandboxRunner`, `verification.sandbox.*`): a Symfony Process runs `php artisan verso:sandbox-plugin` with a fresh SQLite file, `APP_CONFIG_CACHE`/`APP_ROUTES_CACHE` pointing to empty paths, array cache and session, and `VERSO_PLUGINS_PATHS` holding only a copy of the plugin. The child refuses to run unless `VERSO_SANDBOX=1` and the configured SQLite file is the one it was given. It runs core migrations, the plugin migrations up, registers the provider, rolls the plugin migrations back (`PluginMigrator::rollback()`) and prints JSON after `@@verso-sandbox@@` with migrations, new routes, new content types, taxonomies and blocks and errors (stage, message, file and line inside the plugin). Timeouts and runs without a result are high findings.
- Install: a high risk report needs `confirm_slug` equal to the plugin slug (`PluginVerification::installProblem()`); the `extensions.block_high_risk` setting (`VerificationSettings`, default `verification.block_high_risk`, changed on the "Add new" tab of Plugins and themes with `PUT admin.extensions.settings`, capability `manage_settings`) refuses high risk installs. After install the report gets `installed_at`. `verification.reports_kept` reports are kept per plugin, plus the installed one.
- Admin: `admin.plugins.show` (`/admin/plugins/{plugin}`) shows the plugin and its newest report; `admin.plugins.verify` checks the installed files again. The plugins list shows the risk of the newest report. The shared React block is `components/verso/extensions/verification-report.tsx` (`VerificationReportCard`, `RiskBadge`).
- CLI: `php artisan verso:verify-plugin {path} [--json] [--no-sandbox]` takes a plugin folder or zip, prints a table (severity, rule, file, line, finding) or JSON, and exits with 1 for high risk.

### Theme verification

- `Verification\ThemeVerifier` uses the same engine and report. It runs `Checks\ThemeRequirementsCheck` (manifest, required views, parent theme), `Scanners\ThemeScanner` on the theme files, then a sandbox render: `php artisan verso:sandbox-theme` renders the `home`, `entry` and `archive` pages with demo content in a fresh SQLite database.
- Blocking rules stop the install at any risk level: `theme.manifest-invalid`, `theme.missing-view`, `theme.parent-missing` and `theme.render-failed`.
- Install: a high risk theme needs the slug typed to confirm. The `extensions.block_high_risk` setting applies only to plugins (`PluginVerification::installProblem()`).
- Admin: `POST admin/themes/{theme}/verify` (`admin.themes.verify`) checks an installed theme again.
- CLI: `php artisan verso:verify-theme {path} [--json] [--no-sandbox]`.
- How to build a theme that passes: `docs/THEME-GUIDE.md`.

### Theme customizer

- `theme.json` `settings` is an object of fields: `{ "type": "color|font|length|media|size|text|toggle", "label", "help", "default", "css" }`. `font` picks from `options` (keys of the safe list `verso.themes.fonts`). `size` has `min`, `max` and `unit` (any CSS length unit, default px): whole numbers in that unit are stored as numbers and checked against the range, and people may also pick any other CSS unit or a custom value like `clamp(40rem, 80vw, 72rem)`, stored as clean CSS text. `length` is the same without a required range. Both take optional `units` (the units offered, must include `unit`) and `keywords` (from `auto`, `fit-content`, `min-content`, `max-content`, `none`, `normal`). `text` has `max_length` (capped by `verso.themes.setting_text_max`). Only color, font, size and length may set a CSS variable (`--name`). Broken fields are left out; uploads with a broken schema are refused.
- `App\Verso\Theme\Customizer\ThemeCustomizer` saves values as settings `theme.<slug>.<key>` and builds a `:root { ... }` rule with the values that differ from the defaults. The layout gets `$themeStyles` (theme CSS plus that rule), `$themeSettings` (all values) and `$themeLogo` (the first media field, a `Media` or null).
- Admin page `admin.themes.customize` renders a form from the schema with a live preview iframe (`admin.themes.preview`, which renders the home page with draft values from `?values[...]` and saves nothing).
- Plugin tables: put migrations in `plugins/<slug>/database/migrations` and call `$this->loadPluginMigrations()` in `boot()`. They run when the plugin is enabled (`verso.plugins.migrate_on_enable`) and with `php artisan migrate` while it is enabled. Plugin migration prefixes: newsletter `2026_11_17_200000` to `209999`, memberships `2026_11_17_210000` to `219999`, forms `2026_11_17_220000` to `229999`.
- `$this->loadPluginViews('<namespace>')` loads Blade views from `resources/views` of the plugin.
- A plugin block that implements `HasChildBlocks` (`acceptsChild(string $type)`) holds child blocks. The editor shows an inner block list for it (`children: true` in `pluginBlocks`). Render the children with `app(ContentRenderer::class)->renderChildren($block, $entry)`.
- Entry editor panels: a plugin can add a box to the editor side panel with `$this->registerEntryPanel(new MyPanel)`. A panel implements `App\Verso\Plugins\Contracts\EntryPanel` (`key()`, `title()`, `description()`, `appliesTo($type)`, `fields()` with `BlockField` objects). Values are saved in `entries.meta[key]` and checked with the field rules. Panels are shared as the `pluginPanels` prop. Keys `seo`, `comments_open` and `featured_image` are reserved.
- Plugin admin pages live in `resources/js/pages/admin/plugins/<slug>/` and get their URLs as props (plugin routes are not in the Wayfinder files, because they only exist while the plugin is enabled).
- Tests boot a real plugin with `Tests\Support\PluginFixtures::boot('<slug>')` (enable, register, migrate, refresh route names).

### Newsletter plugin (`plugins/newsletter`)

- Tables: `newsletter_lists`, `newsletter_subscribers` (status `pending`, `subscribed`, `unsubscribed`), `newsletter_list_subscriber`, `newsletter_campaigns` (status `draft`, `sending`, `sent`, `blocks` JSON), `newsletter_deliveries` (one row per campaign and subscriber, with a token for tracking) and `newsletter_links`.
- Double opt-in: `Subscribe` stores the address as pending and mails a temporary signed link (`newsletter.confirm`, valid `newsletter.confirm_hours`). Every campaign has a signed unsubscribe link (`newsletter.unsubscribe`, GET or one-click POST) and `List-Unsubscribe` headers.
- The confirm and unsubscribe result pages render the theme view `newsletter.message` (in the plugin `resources/views/theme`, so themes can override it) inside the active theme layout, with `noindex` and `Cache-Control: no-store, private`.
- The `newsletter-signup` block posts to `newsletter.subscribe` (throttled, honeypot field). The answer is the same for new and known addresses.
- Campaign HTML comes from the block renderer (`ContentRenderer::renderChildren`). `SendCampaign` creates the deliveries and queues `SendCampaignBatch` jobs: batch size and delay come from the newsletter settings (`newsletter.batch_size`, `newsletter.batch_delay`, config fallbacks).
- Queue health: the `RecordQueueHeartbeat` job is put on the newsletter queue on the `newsletter.heartbeat_schedule` cron. A worker that runs it stores the time in the `newsletter.queue_heartbeat` setting (`Support\QueueHeartbeat`). When the default queue connection does not use the `sync` driver and no heartbeat was seen for `newsletter.heartbeat_stale_minutes`, the newsletter admin pages get a `queueNotice` prop and show an amber `QueueNotice` (`resources/js/components/verso/newsletter`).
- Open and click tracking are off by default. When on, a 1x1 pixel (`newsletter.open`) and click links (`newsletter.click`, only to links saved for that campaign) are added per delivery. Test sends are never tracked.
- Admin: `admin.newsletter.subscribers.*` (CSV import with a consent check, CSV export, lists), `admin.newsletter.campaigns.*` (editor, test, send, stats) need `newsletter.manage` (editors have it); `admin.newsletter.settings.*` needs `manage_settings`.

### Memberships plugin (`plugins/memberships`)

- Tables: `membership_plans` (`name`, `slug`, `level`) and `memberships` (`user_id`, `plan_id`, `status` `active`, `expired` or `cancelled`, `starts_at`, `expires_at`). A higher level opens everything a lower level opens.
- `MembershipAccess` decides access. An entry is restricted by `meta.membership.plan`: `everyone`, `members` (any active member) or a plan slug. The value is edited in the "Access" entry panel. Users with `memberships.bypass_capability` (editors and admins) always see everything.
- An `EntryContentFilter` (priority 1000) replaces restricted content with the excerpt and a teaser (login link, join link from the `memberships.join_url` setting). An `ApiEntryFilter` empties `blocks` of restricted entries, empties hidden members only blocks and adds `members_only`. The page cache only stores guest pages, so members never get a cached teaser.
- The `members-only` block holds child blocks and shows them only to members (optionally of a plan). Others see the teaser.
- `memberships:expire` runs daily (`memberships.expire_at`) and sends `MembershipExpired`. `AssignMembership` sends `MembershipGranted`.
- Selling plans later: payments are out of scope. A shop plugin can sell a plan by calling `app(AssignMembership::class)->handle($user, $plan, $expiresAt)` when an order is paid, and listen to `MembershipExpired` to offer a renewal.

### AI Assistant plugin (`plugins/ai-assistant`)

- Optional and off by default. Capability `ai.use` (`Capability::UseAi`) is given to editors and admins. The settings and usage page needs `manage_settings`.
- Provider contract `Verso\Plugins\AiAssistant\Contracts\AiProvider::send(AiRequest): AiResponse`. `AiRequest` holds the system prompt, the user content blocks and an optional JSON schema; `AiResponse` holds the text and the input and output tokens. Errors are `AiException` subclasses with a safe message and an HTTP status.
- `AnthropicProvider` calls the Messages API with Laravel Http (no SDK): `x-api-key`, `anthropic-version` (config), `output_config.effort` and `output_config.format` (json_schema) when a schema is given, and server side fallbacks for the models listed in config. Timeout, connect timeout, retries and retry delay come from `config/ai-assistant.php`.
- Plugin settings (`AiSettings`, stored in Settings under `ai-assistant.*`): API key (encrypted), model (default `claude-sonnet-5-5`), max tokens and requests per user per window.
- `AiAssistant` runs the editor actions: outline, rewrite (improve or shorten), excerpt, SEO title and description, image alt text (image sent as base64) and translation (text pieces are pulled out of the blocks and put back, so the block structure stays the same). `AiGuard` refuses to send anything when the plugin is off or the key is empty, and applies the per user rate limit. `UsageLog` adds tokens to the `ai_usage` table (one row per user and UTC day).
- Endpoints: `POST /admin/ai-assistant/actions/{outline,rewrite,excerpt,seo,alt-text,translate}` return `{ result, model }` and never save. The entry editor gets an `entry-sidebar` slot item (`ai-assistant.panel`, props: endpoints, locales, ready) and shows `AssistantPanel`; the user accepts or discards each preview, and accepted changes are saved only with the entry.
- Page editor helper (Easy mode): `POST /admin/ai-assistant/actions/section-text` (`AiAssistant::sectionText`: the text pieces of one section, pulled out of its children like a translation but without image alt text, plus the business description, the site name and tagline and the section label; the answer must keep the number of pieces, which go back into a copy of the section with the same ids) and `POST /admin/ai-assistant/actions/headlines` (`AiAssistant::headlines`: 3 to `targets.headline_count` distinct ideas, each clipped to `targets.headline_chars`). Both use JSON schema answers, `AiGuard`, the rate limit and `UsageLog`, and never save. `PUT /admin/ai-assistant/business` (capability `ai.use`) keeps the business description in the plugin setting `ai-assistant.business_description`; `AiSettings::businessDescription()` falls back to the search description (`seo.default_description`) and then the site tagline. Limits: `limits.max_section_pieces`, `limits.max_business_chars`, `limits.max_section_images` (`AI_ASSISTANT_*`).
- The plugin adds a `page-editor` slot item (`ai-assistant.page-helper`, capability `ai.use`, props: `ready`, `settingsUrl` for admins, endpoints, locales, business description and limits). Its component `PageHelperHost` (`resources/js/pages/admin/plugins/ai-assistant/page-helper/`) puts the props in a small store and shows the open dialog; the plugin builder module (`plugins/ai-assistant/resources/js/builder.ts`) watches that store and registers the "AI helper" top bar button and the section actions "Write this section with AI", "Suggest headlines" and "Describe images" only while the helper is ready (admins without a key get only the button, which links to the settings; other users get nothing). Each dialog shows a before and after preview and applies an accepted result with `context.change()`, one undo step; Discard changes nothing. The top bar menu translates the whole page with the `translate` action (the page title stays) and suggests a headline for the first section with a heading; "Describe images" calls `alt-text` for each picture of the section without a description (image blocks and gallery pictures) and lets people keep or edit each one. Failures show plain messages (`friendlyError`: rate limit and check messages from the server, otherwise "The AI helper is busy. Try again in a minute.").
- A site wide "Translate my site" flow is not built: Verso has no language versions of entries, so translating every page would overwrite the only copy. People translate page by page in the page editor, see each preview and save when they are happy.

### Custom fields (`App\Verso\Fields`)

- A field group (`Definitions\FieldGroup`) has a `key`, `title`, `description`, `position` (`main` or `sidebar`), `order`, `active`, `location` and `fields`. The JSON shape is the same everywhere: export, import, theme and plugin files, `FieldGroup::fromArray()` and `toArray()`.
- Location: a list of rule sets joined by "or"; the rules of one set are joined by "and". A rule is `{param, operator, value}` with `param` `content_type`, `page_template` (`entries.meta.template`), `taxonomy_term` (term id) or `user_role` (the editing user), and `operator` `==` or `!=`.
- Field types (`Enums\FieldType`): text, textarea, rich_text, number, email, url, select, multi_select, checkbox, radio, toggle, date (`Y-m-d`), date_time (site wall time `Y-m-d\TH:i`), color (`#rrggbb`), image, file, gallery (media ids), entry_relation, term_relation, user_relation (id, or ids with `multiple`), repeater (list of rows) and group (object). Settings: `required`, `instructions`, `default`, `placeholder`, `options`, `min`, `max`, `step`, `max_length`, `multiple`, `content_types`, `taxonomy`, `roles`, `min_rows`, `max_rows`, `fields`. `condition: {field, operator, value}` shows a field only when a sibling field equals (or not) a value; values compare as text, so `true`, `1` and `"1"` match.
- Sources: groups made in the admin (`field_groups` table, `Models\FieldGroupRecord`), plugin code (`$this->registerFieldGroup([...])`) and JSON files (`$this->loadFieldGroups()` reads `plugins/<slug>/fields/*.json`; the active theme `fields/` folder is read too, folder name `verso.fields.json_folder`). `FieldGroupRegistry` merges them; a database group wins over a file or code group with the same key. Broken files are skipped and listed on the admin page.
- Storage: values live in `entries.meta.fields` keyed by field name. `EntryRequest` checks them with `Values\FieldValidator` against the groups that match the content type, the picked terms, `meta.template` and the user role. Errors use the input path (`meta.fields.quotes.1.text`). Hidden conditional fields and unknown keys are dropped. Values of groups that do not apply now are kept. The meta keys `fields` and `template` are reserved for entry panels. Limits come from `config/verso.php` `fields`.
- Themes: `field('subtitle')` returns a typed value for the entry of the page (or `field('subtitle', $entry)`); `fields()` returns all. `@field('subtitle')` prints safe HTML, using `$entry` of the view when there is one. Dotted names read inside groups (`address.city`). Types: `FieldImage` (Htmlable, `img()`, src, srcset, sizes, alt), `Media` for files, `Entry` (published only), `Term` and `User` models (collections for `multiple`), `CarbonImmutable` in the site zone for dates, `HtmlString` for rich text, arrays for repeaters and groups.
- REST API: every entry resource has a `fields` object (images with srcset, relations as small objects, users as id and name only). The memberships plugin empties it for restricted entries.
- Admin: `admin.fields.*` (capability `manage_settings`): list, builder, export (`?key=`), import (JSON upload) and copy (a code or JSON group into the database). `admin.fields.lookup` (capability `edit_own_entries`) searches entries, terms and users and returns media by id for the editor. The entry editor gets `fieldGroups` and shows them as section cards; term and template rules are checked live in the browser.

### Forms plugin (`plugins/forms`)

- Tables: `forms` (`title`, `slug`, `fields` JSON, `settings` JSON) and `form_submissions` (`status` `new`, `read`, `spam` or `archived`, `data` JSON, `files` JSON, `email`, `ip_hash`, `user_agent`, `page_url`, `spam_reason`, `search_text`, `read_at`).
- Fields (`Fields\FormField`, `Enums\FieldType`): text, email, phone, textarea, select, checkboxes, radio, date, file (types and size limited by `forms.upload_types` and `forms.upload_max_kb`), consent and hidden (always the builder value). Each field has a label, name, placeholder, help, required, width (`full` or `half` for the multi column layout), options and length limits. `FormField::rules()` gives the submit rules; `Support\BuilderRules` checks the builder data.
- Showing a form: the `form` block (`Blocks\FormBlock`, form picked with a searchable select through the new `BlockField::$searchable`) and `<x-forms-form slug="contact" heading="" intro="" />` for themes. Both use `View\FormRenderer` (view `forms::form`, style and script printed once per page). The form works without JavaScript; the script fetches a fresh CSRF and time trap token from `GET /forms/token` (never cached) when the visitor starts typing, checks fields on blur and submit and moves focus to the first error. Errors use one error bag per form (`form_<slug>`), labels, fieldset and legend for groups, `aria-describedby` and `aria-invalid`.
- `POST /forms/{slug}` (`Actions\SubmitForm`): rate limit per form and IP hash (only valid sends count), validation, optional captcha (`Spam\CaptchaVerifier`, Turnstile or hCaptcha keys in the settings, secret encrypted), then `Spam\SpamGuard`: honeypot and time trap (bots are dropped quietly, or kept as spam with `forms.spam.keep_bot_messages`), links and blocked words (kept as spam, no email). Without JS it redirects back to `#form-<slug>` with a flash, so the page is not taken from the page cache; with `redirect_url` it goes there.
- Emails: `Mail\SubmissionMail` (queued, `forms.queue`) to the form recipients with reply-to set to the sender, and an optional confirmation to the sender. Subjects and bodies use placeholders (`{name}`, `{all_fields}`, `{form_title}`, `{site_name}`, `{submitted_at}`, `{page_url}`), filled by `Support\MailTemplate`; values are escaped.
- Admin (`/admin/forms`, capability `forms.capability`, default `forms.manage`; the inbox needs `forms.messages_capability`, default `forms.messages`; editors have both): forms list, builder, inbox (status tabs, form filter, "sent since" date, search over `search_text`, bulk actions), message view (marks read, file downloads from the private `forms.disk`), CSV export per form (cells that start with `=`, `+`, `-` or `@` are quoted), privacy delete of everything one email sent (`Actions\EraseSubmitterData`). Settings (`manage_settings`): retention days, spam checks and captcha. `forms:prune` and the `forms.prune_schedule` job apply the retention period.

### Shop plugin (`plugins/shop`)

- Enable it on the Plugins page, then run `php artisan migrate` (tables `shop_products`, `shop_product_variants`, `shop_orders`, `shop_order_items`, `shop_order_status_changes`).
- Products are entries of the `product` content type (route base `shop`, so `/shop/{slug}`). Their shop data lives in `shop_products` (one row per entry): `price` in minor units, `sku`, `track_stock`, `stock`, `gallery` (media ids). Variants (`option_name`, `option_value`, own `stock`, optional `price` and `sku`) live in `shop_product_variants`.
- Money is always an integer in minor units. `Support\Money` formats and parses amounts (zero decimal currencies from `shop.zero_decimal_currencies`). `Support\Totals::calculate()` adds flat shipping (free from `free_shipping_over`) and tax in basis points (2100 = 21%), rounded half up.
- Settings use the `shop.*` keys through `Support\ShopSettings` (defaults in `config/shop.php`). Stripe keys are stored encrypted and never sent to the browser.
- The cart is kept in the session (`Cart\Cart`). `Actions\PlaceOrder` turns it into a pending order and takes items out of stock. `Actions\ChangeOrderStatus` moves orders between `pending`, `paid`, `shipped`, `completed`, `cancelled` and `refunded` (`Enums\OrderStatus::next()`), puts stock back on `cancelled` and `refunded`, keeps a history and fires `Events\OrderStatusChanged`.

The `CancelPendingOrders` job runs on the `shop.pending_orders.schedule` cron; `php artisan shop:cancel-pending` does the same by hand.
- Payment gateways implement `Payments\PaymentGateway` (`key`, `label`, `description`, `isAvailable`, `start(Order): PaymentStart`, `instructions`) and are added with `app(PaymentGateways::class)->register()`. Built in: `bank_transfer` and `stripe` (Checkout Sessions over the REST API with Laravel Http). The Stripe webhook at `/shop/webhooks/stripe` checks the `Stripe-Signature` header and marks orders paid or cancelled.
- Public routes (`theme.shop.*`) are never page cached: `/shop`, `/cart`, `/checkout` and the private order page `/checkout/orders/{token}`. Views live in `plugins/shop/resources/views/theme/shop` and `entry-product.blade.php`, so themes can override them.
- Product categories: hierarchical taxonomy `product_category` (`Product::CATEGORY_TAXONOMY`) on products, archive pages at `/{shop.routes.category_base}/{slug}` (default `product-category`, a reserved slug). The core term route renders the plugin view `taxonomy-product_category` and `View\ProductCategoryComposer` adds the products of the category and its sub categories (`Storefront::paginate($sort, $perPage, $category)`), a sort form and sub category links. The shop page lists the top level categories.
- Blocks: `shop-product` (attrs `product`, `showButton`) and `shop-product-grid` (attrs `limit`, `columns`, `sort`, `category`: a category slug or `_all`).
- Admin: Orders (`admin.shop.orders.*`), Products (the stock and price list, formerly Inventory) (`admin.shop.products.*`) and Shop settings (`admin.shop.settings.*`) all need `shop.manage` (`Capability::ManageShop`). Admins have it, and the Shop plugin turns on the optional "Shop manager" role (`shop.manage`, own entries, publish, upload files, manage terms; no site settings or users). Pages are in `resources/js/pages/admin/plugins/shop`.
- Tests boot the plugin with `Tests\Support\ShopFixtures::boot()`.

### Core updates

- Module `App\Verso\Updates`. The running version comes from the `VERSION` file at the root (`config('verso.version')`); git tags are `v` plus that version. `App\Verso\Core\Support\Version` parses and compares semantic versions (`parse`, `tryParse`, `compare`, `isNewerThan`, `isPreRelease`, `isSameMajor`, `isSameMinor`).
- Release feed: `verso.updates.feed_url` (default the GitHub releases API of victoragudo/verso, empty turns checks off) in the GitHub releases format. A release needs the asset `verso-<version>.zip` (`asset_name`), a `<zip>.sha256` file and optionally a `<zip>.sig` file (base64 detached Ed25519 signature). Drafts, bad tags and releases without a package are skipped. A title or notes with `[security]` (`security_marker`) marks a security release. `ReleaseFeed::latestFor()` picks the newest release for the channel (`stable` skips pre-releases).
- `UpdateChecker::check()` reads the feed and caches the releases (`cache_key`, `cache_ttl`); `status()` only reads the cache, so pages never call the network. The scheduled `CheckForUpdates` job (`check_schedule`, daily) refreshes it and installs automatic updates.
- Settings (`UpdateSettings`): `updates.channel` (`stable` or `beta`) and `updates.automatic` (`off`, `security` for security patches of the same minor version, `minor` for minor and patch releases of the same major version). New major versions always wait for a person. Automatic updates never run without a database backup.
- `CoreUpdater::start()` creates a waiting row in the `updates` table (one at a time, only newer releases, consent needed when the database cannot be backed up). `run()` logs every step (`UpdateStep`) in `updates.steps`: lock (a file lock, `UpdateLock`), download (`max_download_kb`, `download_timeout`), verify (sha256, plus the signature when `public_key` is set), unpack (safe names, `VERSION` must match), maintenance mode, database backup (SQLite `VACUUM INTO` copy, `mysqldump` or `pg_dump` when found), core files backup, copy, `migrate --force`, `optimize:clear`, `up`, health check (`health_check.paths` on `health_check.base_url` or APP_URL), cleanup (keeps `backups_kept` backups). Artisan steps run in a new PHP process inside `install_path`.
- Kept paths (`keep_paths`): `.env`, `storage`, `plugins`, `themes` (except `replace_paths`, so `themes/default` is replaced), `public/uploads`, `public/storage`, the SQLite file, `bootstrap/cache`. A top-level folder of the package is replaced as a whole, so files removed from the release disappear. Files the package does not list (like a custom favicon) stay.
- Any failure after files or the database changed rolls back: maintenance on, files restored from `storage_path/backups/<id>`, database restored, caches cleared, site up. The run ends `rolled_back` (or `failed` when nothing had changed).
- Admin page `admin.updates.index` (capability `manage_updates`, admins only): versions, changelog (markdown rendered with raw HTML escaped and unsafe links dropped), "Update to X" (runs after the response, or on the `queue` when `run_after_response` is off), live progress by polling (`poll_interval`), settings and the log. The dashboard shows a notice through `Dashboard::addNotice(new DashboardNotice(...))`.
- CLI: `php artisan verso:update` (`--check` only checks, `--yes` skips questions, `--rollback` restores the last completed update from its backup).
- Release packages: `.github/workflows/release.yml` runs on `v*` tags (the tag must match `VERSION`) and attaches the zip, the sha256 file and, when the `VERSO_RELEASE_SIGNING_KEY` secret is set, the signature. `scripts/build-release.sh [ref]` builds the same into `dist/`.
- Tests use `Tests\Support\UpdateSandbox`: a fake site in a temporary folder with its own SQLite file, release zips and GitHub feed data. HTTP calls are faked with `Http::fake` and artisan calls with `Process::fake`.

### Performance and caches

- Details, numbers and the benchmark are in `docs/PERFORMANCE.md`.
- Public routes use `ThemeServiceProvider::PUBLIC_MIDDLEWARE`: `verso.cache.early` (`ServeCachedPage`, before the session starts), `web`, `verso.redirects`, `verso.theme`, `verso.adminbar` (`InjectAdminBar`, outside the page cache), `verso.cache` (`CachePage`, stores misses), `verso.footer`. `MarkPageCacheBypass` (end of the `web` group, in `bootstrap/app.php`) sets the `verso_nocache` cookie (`verso.page_cache.bypass_cookie`) for signed in visitors and pending flash data; visitors with it never get an early hit. Cached pages carry `ETag` and `Last-Modified` and answer `304`.
- Admin bar (`Theme\AdminBar\AdminBar`, view `verso-theme::admin-bar`): `InjectAdminBar` adds it right after `<body>` of public HTML pages (also the Shop public routes) for users with `view_admin_bar` (admins only) whose `users.show_admin_bar` is on (profile setting, default on). It runs outside `CachePage`, so the bar is never stored; signed in users carry the bypass cookie and never get an early hit. Never on redirects, JSON, Inertia visits, `/admin`, feeds, the sitemap or robots.txt (`Support\HtmlResponse::is()`). `ThemeResponse::entry()` records the shown entry in the scoped `AdminBarContext` for the "Edit post" link (only when `update` is allowed); when the Easy mode page editor route exists, "Edit" opens it and the entry editor moves to an "Advanced editor" menu. The bar goes after the real `<body>` tag: `InjectAdminBar::bodyEnd()` skips comments, styles, scripts and other raw text elements. Inline scoped CSS (`.verso-adminbar`), native popovers for the New and user menus, `--verso-adminbar-height` for themes, config `verso.admin_bar.enabled` and `height`.
- Caches with their own invalidation: `Site\Menus\MenuCache` (menu trees per location, used by `MenuRenderer::links()` and `hasItems()`), `Core\Support\ManifestCache` (theme and plugin manifests and Composer plugin packages, keyed by file inode, times and size), `Plugins\BlockOutputCache` (core block HTML per entry, keyed by a hash of the blocks; entries with plugin blocks are never cached; `EntryContentFilter` always runs after it). Code that changes what blocks render outside the blocks themselves must call `BlockOutputCache::flush()`.
- `Media\ResponsiveImages` is scoped to one request. Call `preloadEntries($entries)` before rendering a list of entries so their images load with one query.
- `Model::preventLazyLoading()` is on outside production. Eager load relations or use `Entry::loadedParent()`.
- Query budgets live in `tests/Support/QueryBudget.php`. A new query on a key page must fit the budget, and list pages must not grow with the number of entries.
- `php artisan verso:benchmark [--entries=] [--requests=] [--warmup=]` seeds a temporary SQLite database in a child process and fails when a route is over the `verso.benchmark` budgets.

### Site Editor and block styles

The Site Editor lets people build the whole site with blocks, so no page builder, header, footer or mega menu plugin is needed. The parts in place now:

- **Edited parts** (`App\Verso\Site\Parts\SitePartStore`, tables `site_parts` and `site_part_revisions`). One row per theme and part key (`header`, `footer-minimal`). `blocks` is the working copy (draft), `published_blocks` is what visitors see. Publishing keeps a revision (`verso.site_parts.max_revisions`) and fires `SitePartPublished`, which empties the page cache. "Restore original" deletes the row. Theme files are never written. `@templatePart` asks `TemplateParts::render()`, which tries the edited variant, the variant file, the edited base part and the base file, in that order. `SitePartStore::preview()` shows unsaved blocks for one request (the editor preview).
- **Block styles** (`App\Verso\Editor\Styles`). Every block, core, site or plugin, can carry `attrs.design` (not `style`: the button block uses that name for its look; a block that declares its own `design` or `customCss` field keeps it). `BlockStyleSchema::OPTIONS` lists each option path (`spacing.padding.top`, `layout.columns`, `typography.fontFamily`, `color.overlay`, `border.radius`, `shadow`, `position.sticky`, `visibility.hidden`...) with its CSS property and value kind. A value is plain or responsive: `{"base": "3rem", "tablet": "2rem", "mobile": "1rem"}` (widths in `verso.editor.breakpoints`). Values are sizes, hex colors, fixed keywords or design tokens like `var:color.accent`, printed as `var(--verso-color-accent)`. Sizes (kinds `length`, `angle`, `time`) are checked by the shared CSS value parser (`App\Verso\Core\Css\CssValueParser`, `resources/js/lib/css-value.ts`, cases in `tests/Fixtures/css-values.json`) with the value rule of each property: every CSS unit, the keywords the property takes, plain numbers where allowed (line height) and custom values made only of numbers, units, `calc()`, `clamp()`, `min()`, `max()` and `var(--name)` (200 characters, 6 levels at most). Values are stored as clean strings like `"1.5rem"` or `"clamp(1rem, 2vw, 2rem)"`; old plain numbers on a length read as pixels (`24` is `24px`). Free CSS text is never accepted in `design`. `ValidBlocks` checks styles for every block; `attrs.customCss` (declarations only, sanitized) needs `verso.editor.custom_css_capability`.
- **Rendering**. `BlockRenderer` asks `BlockStyleCompiler` for one class per distinct style (`vs-<hash>`), adds it to the first tag of the block HTML and prints all rules once in a `<style data-verso-block-styles>` before the outermost render. Block renderers do not need to know about styles.
- **Live styles in the editor canvas**. `resources/js/builder/style-css.ts` is a TypeScript port of the schema checks and the compiler; `tests/Fixtures/block-styles.json` holds cases that both a Pest test and a Vitest test compile, so the two cannot drift (each style property sends its `css` name in the editor manifest). The canvas prints one `<style data-verso-canvas-styles>` with a `vs-e-<block id>` class per styled block, using the values of the screen size picked in the Computer/Tablet/Phone switch (`builder/device.ts`), and narrows the canvas to that width. Layout properties go on the child list (`vs-e-<id>-c`), and blocks hidden on a screen size are faded, not removed.
- **Section block** (`section`): a box that holds any blocks, nested sections too, with a choice of HTML element. With `layout` styles it is the flex or grid primitive of headers, footers and landing pages, next to `columns`.

- **Style presets** (`Editor\Styles\StylePresets`). `attrs.preset` names a preset (core: `card`, `hero`, `pill`; theme: `editor.presets` in theme.json; saved: setting `editor.style_presets`, routes `admin.editor.presets.*`, capability `edit_styles`). The compiler puts the block styles on top of the preset styles (`array_replace_recursive`, also per screen size); the canvas does the same in `builder/style-css.ts`. Other style kinds: `gradient` (linear or radial, 2 to 5 hex or token stops), `image` (a safe site path or http(s) address), `focal` (`"30% 70%"`), `zIndex`, and background size, repeat and attachment keywords. A gradient and a picture join in one `background-image`. `tests/Fixtures/block-styles.json` holds the cases and the presets both sides compile.
- **Builder blocks** (`App\Verso\Blocks`, provider `BlocksServiceProvider`). One class per block on `Blocks\Support\ModuleBlock` (a plugin block with fields that draws with the block renderer): layout (`grid`, `stack`, `spacer`, `shape-divider`), interactive (`tabs`/`tab`, `accordion`/`accordion-item`, `toggle`, `slider`/`slide`, `image-compare`, `video-background`, `icon`, `icon-list`/`icon-list-item`, `counter`, `progress-bar`, `timeline`/`timeline-item`, `alert`, `countdown`, `social-share`, `table-of-contents`, `modal`, `mega-menu`, `mobile-menu`) and dynamic (`post-title`, `post-featured-image`, `post-content`, `post-excerpt`, `post-date`, `post-author`, `post-terms`, `post-field`, `post-reading-time`, `breadcrumbs`, `archive-title`, `query-loop`). The gallery block has a `lightbox` switch and the `map` block comes from Easy mode. Testimonials, prices, team, FAQ and calls to action are the Easy mode ready sections, offered in the Add panel ("Sections"). CSS and JavaScript live in `resources/blocks/<asset>`, are registered in `Editor\Assets\BlockAssetRegistry` per block type, served by `GET /verso-blocks/{asset}.{css|js|json}?v=<hash>` (immutable caching) and printed by `BlockRenderer::withStyles()` around the blocks that need them (stylesheets before, module scripts after), so pages without those blocks load nothing. Scripts follow Modern Web Guidance (native `<details>`, `<dialog>` with `closedby`, invoker commands with click fallbacks, popover, scroll snap, `prefers-reduced-motion`) and no block prints a `style` attribute. The bundled icon set (`Editor\Icons\IconLibrary`, Lucide ISC, `resources/blocks/icons/icons.json` built by `scripts/blocks/build-icons.mjs`) also serves the icon picker.
- **Render context** (`Editor\Support\RenderContext`, scoped). `ThemeResponse::render()` records the kind of page, its subject and its data; `ContentRenderer::render()` and the query loop push the entry being drawn. Dynamic blocks and layout conditions read it.
- **Theme builder** (`App\Verso\Layouts`, tables `site_layouts` and `site_layout_revisions`, admin `admin.theme-builder.*` under Design, Theme builder). A layout is a template, header, footer or popup built with blocks, with rules from `Layouts\Conditions\ConditionRegistry` (core: everywhere, kind of page, content type, one entry, term, author, visitor, role) and a priority; the best match wins (priority, then the weight of the rule, then the newest). Drafts autosave, Publish keeps a revision and empties the page cache. Templates draw through `Theme\Templates\TemplateOverrides` inside the theme layout (`verso-layouts::template`), headers and footers replace `@templatePart('header')` and `('footer')`, top bars go above the header, and modal, slide-in and cookie popups are printed by `ThemeFooterFilter`. Popup triggers, frequency and screen sizes run in the browser (`resources/blocks/popups`); choices stay in browser storage. Capabilities: `edit_templates` (templates, headers, footers) and `edit_popups`, both implied by `edit_site`.
- **Builder workspace** (`resources/js/components/verso/workspace`). The theme builder, the Site Editor part editor and the library item editor use `BuilderWorkspace` inside the admin frame (`WorkspaceLayout`, `AdminShell workspace`): a top bar, then panes that fill the screen height and scroll on their own (Add blocks or Outline panel, block canvas, preview, settings). Canvas and preview are split by `SplitPane` (a `role="separator"` that moves with the pointer or the arrow keys). Defaults follow the workspace width (`workspace-mode.ts`, `@container/workspace`): every pane from 150rem, the settings stay open from 100rem, canvas and preview with toggles from 64rem, Edit and Preview tabs below. Sizes, open panels, closed tips and focus mode (hides the admin sidebar and top bar) are kept per user in localStorage (`verso.workspace.<userId>.*`). `PreviewPane` draws the computer page at least `verso.site_parts.preview_desktop_min_width` wide and scales it to fit. `LayoutPreview::targets()` marks each preview page with `usesLayout` from the layout rules, so the editor opens on a page the layout applies to and says when the picked page does not use it. The canvas toolbar (`OverflowToolbar`) moves groups that do not fit into a More menu.
- **Design library** (`App\Verso\Library`, table `library_items`, admin `admin.library.*`, capability `manage_library`, editors have it). Blocks or selections are saved from the editor as a synced block (the `synced` block points to the item) or a pattern (copied when added). The Add panel has a Library tab; the library page lists saved items and theme and plugin patterns, edits them and imports or exports JSON (`format` 1).
- **Caching**. Static builder blocks implement `Plugins\Contracts\CacheableBlock`, so entries made of them stay in the block output cache; the cache key holds a fingerprint of the presets the entry uses. The usage index records synced blocks (`synced`, key `ref`) and presets (`style-preset`), so a changed library item or preset only forgets the cached pages that use it, unless a header, footer or layout uses it.
- **Editor**: a breadcrumb of the selected block, a zoomed out view (CSS `zoom: 0.5`) and revision comparison (`GET admin.entries.revisions.compare`, `Editor\Support\BlockDiff`) side by side with added, removed, changed and moved blocks marked.

### Easy mode (`App\Verso\Easy`)

Easy mode lets a person with no technical knowledge build a simple site. Module layout: provider `EasyServiceProvider`, admin routes `routes/verso/easy.php` (`admin.easy.*` under `/admin/easy`), config `verso.easy` (`VERSO_EASY_*`), settings `easy.*` (`Easy\Support\EasyState`: `easy.starter`, `easy.started_at`, `easy.style_preset`, `easy.font_pair`, `easy.styled_at`, `easy.launched_at`, `easy.privacy_page`; `Easy\Simple\SimpleMode`: `easy.simple_mode_default`), React pages in `resources/js/pages/admin/easy`, components in `resources/js/components/verso/easy`, helpers in `resources/js/lib/easy`, tests in `tests/Feature/Easy`, `tests/Unit/Easy` and `resources/js/tests/easy`.

- **Ready sections**: `Sections\SectionLibrary` holds `SectionTemplate` items that turn `SectionContent` into core blocks styled with theme tokens (`attrs.design` with `var:` values). `SectionKit` makes the blocks with unique ids. The `map` block (`Blocks\MapBlock`) is registered in the plugin block list and the block registry, like site blocks.
- **Starter sites**: `Starters\StarterSiteRegistry` holds `StarterSite` value objects (pages made of sections, menus, settings, plugins, a style preset key and sample pictures). `Actions\InstallStarterSite` turns plugins on (outside the transaction, because plugin migrations may change the schema), paints the pictures, then creates or updates pages, menus and settings in one transaction. It never duplicates a page: pages made by a starter (`entries.meta.easy_starter`) are updated, the site's own pages are kept.
- **Guided start**: `admin.easy.start` ("What is your site for?", capability `manage_settings`) shows the starters as radio cards; the POST installs one and opens "Make it yours" with a toast (the dashboard for people who cannot manage themes). After the install, `WelcomeController` opens the guided start while `easy.starter` is empty (`verso.easy.guided_start_after_install`). The dashboard notice `easy-start` invites admins before a starter is chosen and stays as a quiet link after. Menu: Design, Guided start.
- **Make it yours**: `admin.easy.style` (capability `manage_themes`) lets people upload a logo, take a palette from it (read in the browser by `resources/js/lib/easy/palette.ts`: canvas pixels, grouped colors, an accent, then light, dark, soft and two color palettes, all made readable), set each color role, pick a font pair and a style preset. The page shows the real home page in the Site Editor preview frame (`admin.site-editor.preview` with `?tokens[...]` and `?logo=<media id>`, `0` for none), reloaded `verso.easy.preview_delay` ms after the last pick, at computer, tablet or phone width. `Styles\ThemeStyleOptions` cuts presets, font pairs and color roles down to the tokens the active theme declares and accepts. Saving runs `Actions\ApplyEasyStyle`: `GlobalStyles::save()` for the tokens, `ThemeCustomizer` for the logo (`ThemeCustomizer::logoField()`, the first media field), and the settings `easy.style_preset`, `easy.font_pair` and `easy.styled_at`. `Styles\ContrastChecker` and `contrast.ts` share WCAG rules and the fixture `tests/Fixtures/contrast.json`; hard to read colors are saved with a warning toast, and the page shows plain warnings with a "Fix it" button. The guided start POST opens this page; the dashboard notice `easy-style` invites admins after a starter until they save once. Menu: Design, Make it yours.
- **Visual page editor**: `admin.easy.pages.edit` (`/admin/easy/pages/{entry}`, full screen page `admin/easy/page-editor`, allowed when the user may `update` the entry) shows the real page in a same origin frame (`srcdoc`). The admin bar "Edit page" button opens it for the shown entry; the entry editor stays one click away as "Advanced editor" (admin bar menu and the editor's More menu). `POST admin.easy.pages.frame` (`Pages\PageFrame`) draws the entry with the active theme (`ThemeManager::registerViews()`, because admin requests only know the fallback views, then `ThemeResponse::entry()` on an in memory copy) from the unsaved blocks of the editor, checked by `ValidBlocks`, never saved, `Cache-Control: no-store`, `X-Frame-Options: SAMEORIGIN`, no admin bar. It turns on edit mode in `BlockRenderer::showMarkers()`: the first tag of every block gets `data-verso-block` and `data-verso-type` (and `data-verso-hidden`), hidden blocks stay on screen, and `ContentRenderer` skips the block cache. `resources/js/lib/easy/frame-bridge.ts` makes that document editable: click (or Enter) to edit headings, paragraphs, lists, quotes, citations, captions and button labels (plain inline marks, plain text paste, Enter ends single line texts, Escape cancels), "Replace image" on image blocks and gallery pictures (media picker), a toolbar on every top level block ("section": Move up, Move down, Duplicate, Hide or Show, Delete with an Undo toast, plus `builder.pageSectionActions`), one tab stop per toolbar with arrow keys, and "Add section" rows that open the gallery of `SectionLibrary::toArray()`. `GET admin.easy.sections.build` builds a section on the server with fresh ids and the latest pictures of the media library (`Sections\SectionPictures`, `verso.easy.section_pictures`). The editor keeps one undo history of the blocks (`lib/easy/page-history.ts` on `builder/history.ts`, `verso.easy.page_editor.undo_steps`), draws the frame `render_delay` ms after the last change (keeping the scroll position and waiting while a text is edited) and moves focus back to the button that was used. `PUT admin.easy.pages.update` saves through `Actions\SaveEasyPage` and `UpdateEntry` (revisions, events, caches): "Save" keeps the status, "Publish" needs the `publish` right. A block hidden on every screen size (`attrs.design.visibility.hidden` true) is left out of the public page by `BlockRenderer`.
- **Safety nets**: the page editor keeps unsaved changes as an automatic draft `verso.easy.page_editor.autosave_delay` ms after the last change (`PUT admin.easy.pages.draft`, `Drafts\PageDrafts`, table `easy_page_drafts`: blocks per entry and person, checked by `ValidBlocks`, never shown on the site, no revision, no cache change). Offline or on a failed request the blocks go to `localStorage` (`resources/js/lib/easy/page-drafts.ts`, `use-autosave.ts`) and are sent when the connection is back; a polite status says "All changes saved as a draft", "Saving…" or "Offline, saved on this device". A draft newer than the page (server or device copy, `pickDraft()`) opens with a banner "Keep editing them / Throw them away" (`DELETE admin.easy.pages.draft.discard`); older drafts are dropped. `SaveEasyPage` clears the draft after a save. "Restore this page" (More menu) lists the last `verso.easy.page_editor.versions` revisions (`GET admin.easy.pages.versions`, `Pages\PageVersions`: time, author, "3 sections"), previews one through the frame endpoint and puts it into the editor as one undo step; it reaches visitors after Save, which keeps the current content as a revision. Every change (text, picture, section actions, AI changes, draft, restore, "Start over") is one undo step; Ctrl or Cmd+Z, Shift+Z, Y and S also work while the frame has focus (`frameShortcut()`), typing keeps the browser's own undo. "Start over" goes back to the last saved blocks after a confirm. Publishing an empty page needs `confirmEmpty` (the editor asks), deleting the last section of the home page asks first. `resources/js/lib/easy/plain-errors.ts` turns 419, 403, 413, 422, 5xx and lost connections into plain sentences with a next step for the page editor, "Make it yours" and the guided start (Inertia `onHttpException` and `onNetworkError` return false, so the error dialog never opens); on a failed save the blocks also go to the device copy. An empty page marks its content area with `data-verso-empty` in edit mode, where the frame shows "Add your first section"; on phone widths the section toolbar stays in the flow so it never covers "Add section", and it shows only for the selected section or keyboard focus (`:has(:focus-visible)`), never for a tap that only focuses a text (the text would move before the tap ends); a section that gets focus after an action is selected. Phones show the save state under the top bar (`save-state-phone`). The previews of the page editor and "Make it yours" show a label with the device and its width. "Make it yours" has "Undo" for the last pick (`lib/easy/choice-history.ts`, `undo_steps`) and "Back to the colors I had" (the saved picks); the preview never saves.
- **Simple admin mode**: per person in `users.admin_preferences.simple_mode` (`AdminPreferences::simpleMode()`), falling back to the setting `easy.simple_mode_default` (saved as true by the install step `SaveSettings` and by the first starter site, `verso.easy.simple_mode.new_sites`) and then to `verso.easy.simple_mode.default` (false). `Simple\SimpleMode` answers it; the provider shares the props `simpleMode` and `routeName` with `Inertia::share()`. An `AdminNavFilter` (priority 1000) keeps only the keys of `Simple\SimpleModeNav` and renames some items with plain words, so the sidebar and Cmd+K shrink; hidden pages still open by URL. `PUT admin.easy.simple-mode.update` switches it (any signed in person); the switch is in the account menu, the profile page (slot `profile-sections`) and the help panel. In simple mode the dashboard keeps only stats and panels that lead to menu pages, with plain names, and the page list adds "Edit on the page".
- **Launch checklist**: `Launch\LaunchChecklist` of `LaunchCheck` steps (core: `Launch\CoreLaunchChecks`, including `readable-colors`), shown by `Launch\LaunchChecklistCard` in the new slot `dashboard-top` for people with `manage_settings`, in simple mode or after a starter site, until they hide it once every step is done (`POST admin.easy.launch.dismiss`). "Create a privacy page" (`POST admin.easy.launch.privacy`, `Actions\CreatePrivacyPage`, setting `easy.privacy_page`, slug `verso.easy.privacy.slug`, a new page is added to the end of the menu in `verso.easy.privacy.menu_location`, `footer` by default) and "Go live" (`POST admin.easy.launch.go-live`, `Actions\GoLive`: `reading.discourage_search` off and `easy.launched_at`). "Your site details" (`admin.easy.details`) saves `site.contact.*`, `seo.schema_same_as`, `site.tagline` and `seo.default_description`; new contact sections use the contact details and an empty `social-links` block shows the social profiles.
- **AI helper**: with the AI Assistant plugin on and a key saved, the page editor gets an "AI helper" button and section actions (write a section from a short business description, suggest headlines, describe pictures, translate the page). Everything lives in the plugin (see "AI Assistant plugin"); core only offers the `page-editor` slot and the page editor registries, so Easy mode works the same with the plugin off.
- **Help panel**: the "Help" button of the admin top bar opens a sheet (`components/verso/easy/help-panel.tsx`) with topics from `Help\HelpTopics` (`GET admin.easy.help`, loaded once when it opens), the topics of the current route first, a search box, inline SVG drawings and optional videos (`verso.easy.help.videos`).
- **Accessibility and tablets**: every Easy mode screen targets WCAG 2.2 AA and works with touch at 768x1024 and 1024x768. Buttons and fields use `TOUCH_TARGET` (`components/verso/easy/touch.ts`: 44px for fingers, `pointer-fine:md:min-h-9` with a mouse), the page editor top bar stays at 44px, and the admin bar grows its buttons under `@media (pointer: coarse)`. Nothing needs hover: tapping a section selects it and shows its toolbar (`.verso-easy-active`, kept across redraws by `EditorFrame` through the bridge `selected` and `onSelect` options), tapping a text edits it, "Replace image" is always on screen. "Make it yours" puts the controls and the preview side by side in landscape from a 42rem page container (`landscape:@2xl/page:`) and stacks them in portrait; the logo box and the save bar use container queries. Dialogs opened from a button inside the frame (section gallery, media picker, AI helper) give focus back to that button (`lib/easy/return-focus.ts`, `pageHelper.returnFocus()`); after a picture change focus goes to its "Replace image" button (`FrameFocus` kind `image`). Section boxes without a landmark tag get `role="group"` with their name (a section named after its heading follows edits of that heading, `setText()`); badges say "Hidden on your site" and "Colors hard to read" in words. Colors beyond "Make it yours": the page editor gets the color tokens of the style (`colors`, `ThemeStyleOptions::colorValues()`), `lib/easy/section-colors.ts` checks text in sections that set `attrs.design.color.text` or `color.background` (tokens or hex, base value of responsive options, unreadable values skip the check) against the WCAG minimums of `contrast.ts`, and the section gets a warning badge, an `aria-description` and a "Fix colors" toolbar button that sets a readable text color token on the block that set the colors (one undo step). The launch checklist step `readable-colors` ("Make your colors easy to read") is done while `ContrastChecker::review()` finds nothing in the saved palette (`ThemeStyleOptions::palette()`). The `sections` part of `tests/Fixtures/contrast.json` is read by Vitest and Pest. On "Make it yours", typing in one color box (or dragging its picker) is one Undo step until the box loses focus (`pickChoice()` merge keys, `settleChoice()`); a style brings its font pair only while the person has not picked fonts on the page (`suggestedFontPair()`). Tests: `resources/js/tests/easy/accessibility.test.tsx` runs axe-core (dev dependency, helper `resources/js/tests/axe.ts`, color contrast and regions are checked in a real browser) on every screen and dialog, and `tests/Feature/Easy/AccessibilityTest.php` checks the admin bar and the edit mode markers.
- **Browser journey**: `tests/e2e/easy-journey.spec.ts` (Playwright, `npm run test:e2e`, config `playwright.config.ts`) runs a fresh web install to a finished site at 1440x900 and 390x844 (touch); `tests/e2e/builder-landing.spec.ts` builds a landing page with the builder and the theme builder at 1440, 1024 and 390; each against its own server from `scripts/e2e/serve.mjs` (PHP built-in server with `scripts/e2e/router.php`, a throwaway SQLite file, storage folder (`LARAVEL_STORAGE_PATH`), `.env`, lock and state files in the temp folder, so the developer's `.env` and database are never touched). Helpers in `tests/e2e/support` check sideways scroll, run axe-core and time the steps. Results and usability notes: `docs/QA.md` ("Easy mode journey"). `tests/e2e/fresh-install.spec.ts` (`npm run test:e2e:install`, config `playwright.install.config.ts`) runs the documented install instead: `scripts/e2e/fresh-install.mjs` makes a project with `composer create-project` from the checkout, serves it with `php artisan serve` and the test runs the wizard and an admin login.
- Registries and their contracts are documented in `docs/EXTENDING.md` ("Easy mode registries").

## Database portability

Every query must work the same on SQLite, MySQL 8.4 and PostgreSQL 17. CI runs the full suite on all three (`.github/workflows/ci.yml`), and `scripts/test-databases.sh` does the same locally with Docker.

- Text search: use `App\Verso\Core\Database\TextSearch::apply($query, ['title', 'excerpt'], $term)`, never `where(..., 'like', ...)`. It ignores case (Postgres `like` does not) and escapes `%` and `_`.
- JSON columns that are edited (`entries.blocks`, `entries.meta`, `media.meta`) use the `App\Verso\Core\Database\JsonArray` cast. MySQL returns JSON object keys in its own order, and this cast does not count a new key order as a change. In tests, compare data read back from JSON columns with `toBeJsonData()`, not `toBe()`.
- Text compare: MySQL ignores case by default. A column whose case matters (like `redirects.from_path`) needs a binary collation on MySQL.
- Sorting: add `id` as the last sort key when you paginate by a value that is not unique (name, title, date).
- Schema: no database-specific column types. Do not drop or rename tables that other tables reference inside tests.

## Admin design system

The admin must look elegant and calm, in the style of the Cloudflare dashboard. Build it with shadcn/ui components from `resources/js/components/ui`.

- **Font:** Figtree (self-hosted, variable, weights 400 to 700). Tabular numbers for stats and tables.
- **Colors:** light and gray. App background `zinc-50`, surfaces white, borders `zinc-200`, body text `zinc-700`, headings `zinc-900`, muted text `zinc-500`. Primary buttons `zinc-900` with white text. One quiet accent (blue 600) only for links, focus rings and active nav. Status colors are soft badges (green, amber, red, gray) with 50 background and 700 text. No gradients, no heavy shadows (only `shadow-xs` on cards).
- **Layout:** fixed left sidebar (240px) with the site name and a site switcher area on top, nav grouped in sections with small uppercase labels that open and close (Content, Design, Tools, Administration, Settings), active item with a light gray background and accent icon. Top bar with breadcrumbs, a command search (Cmd+K) and the user menu. Content area uses the full width next to the sidebar with fluid side padding (`admin-gutter`); `<main>` is the `page` size container. Card lists use `auto-grid` or `auto-fit-grid` with `[--grid-min:<width>]` and wide pages adapt with `@container/page` queries, not viewport breakpoints. Only long text keeps a reading width (`max-w-prose`). Page header with title, short description and actions on the right.
- **Full width:** Every admin screen, editor and wizard uses the full width of the screen, including ultrawide monitors: no fixed max width containers with empty space around them; use intrinsic grids, container queries, more columns or side by side panels, and clamp() gutters; check at 3440, 2560, 1920, 1440 and 390 px. The full screen editor canvas is fluid (`@container/canvas`, clamp side padding); only text blocks keep a reading measure, and the "Content width" choice in the editor menu (Full width or Reading width, kept in localStorage) narrows the canvas for people who want it.
- **Components:** cards with 8px radius and 1px border, section cards with a header row. Dense tables with sticky header, row hover, inline actions in a menu. Empty states with an icon, one line and one action. Forms in two columns on desktop (main fields left, meta panel right like publish, status and SEO).
- **Responsive:** sidebar becomes a sheet under `lg`. Tables turn into stacked cards under `md`. Touch targets at least 40px. No horizontal page scroll at 360px.
- **Icons:** a custom Verso icon set in `resources/js/components/verso/icons/` (one React component per icon, 20px grid, 1.5px stroke, round caps and joins, `currentColor`). Nav items and page headers use these icons, referenced by key (for example `icon: 'entries'`). Lucide is allowed only for tiny generic controls (chevrons, close, check).
- **Dark mode:** supported but light is the default.

## Quality rules

- Lots of tests. Every action, model method, controller, command and renderer has Pest tests. Feature tests for every admin page and public route. Use realistic data (real-looking titles, names and text), never "foo" or "test".
- Frontend work (HTML, CSS, client side JS and React, Blade themes) follows Modern Web Guidance. Before building a UI pattern, run `npx -y modern-web-guidance@latest search "<2-5 word capability>" --skill-version 2026_11_10-47b4c80e`, then `retrieve "<id>"` and apply the guide. Browser support policy: Baseline Widely available features are used freely; newer features only with the fallback the guide recommends. Run `npx -y modern-web-guidance@latest legacy-scan resources themes plugins` before finishing frontend changes.
- Brief code comments in simple English (B1 level). One short line per class and per non-obvious method. No long docblocks.
- `php artisan test`, `vendor/bin/pint --test`, `vendor/bin/phpstan analyse --memory-limit=1G` and `npm run types:check` must pass.
- Tests in `tests/Feature`, `tests/Unit/Core` and `tests/Unit/Content` boot Laravel with `RefreshDatabase`. Add your `tests/Unit/<Module>` folder to `tests/Pest.php` if it needs Laravel. Vite is disabled in tests.
- Domain rules go in models and actions, not in controllers.
- Admin JavaScript has Vitest tests (`npm test`) in `resources/js/tests/<area>/*.test.ts(x)`, run in jsdom with the process time zone set to `Pacific/Auckland` so code that uses the computer zone fails. Mock Inertia with `vi.mock('@inertiajs/react', async () => (await import('@/tests/mocks/inertia')).inertiaMock)` and set page props with `setPageProps()`. Mock `media-api` (or other fetch helpers) instead of calling the network. Wayfinder route files are generated before the run when missing.
- No hardcoded operational values: put them in `config/verso.php` (with env overrides) or in Settings.
- Atomic commits: one logical change per commit, clear English message.
